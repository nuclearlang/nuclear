# NuclearLang dialects

A **dialect** is a set of TOML files that teaches the transpiler a target language or a framework. The base
transpiler (lexer, parser, resolver and emitter) knows no target language: everything it writes comes from
the templates and tables of the active dialect. Dialects are read at run time, so they can be created or
changed without recompiling the transpiler.

Every dialect uses the same format, described in this document. The full tables of templates, variables and
options are generated by the transpiler: `nuclear spec`.

## Golden rule

Every dialect (target, framework or project) follows NuclearLang's golden rule
([nuclear-base.md §1](nuclear-base.md)): **performance, speed and readability of the syntax**.

- **Performance:** the generated code is what an expert in the target would write so it runs as fast as
  possible (`const` constructors, no layers nor indirections that add nothing at run time, no reflection).
  The architecture a kind generates exists in the output only if the application uses it.
- **Speed:** transpiling is immediate (the transpiler reads only the index of each definitions package) and
  the generated code compiles without extra steps the developer has to remember.
- **Readability:** what is written in Nuclear is the minimum. A kind or shortcut exists to remove repeated
  code, never to add a second way of writing the same thing.

## 1. Kinds of dialect and inheritance

| Kind | What it defines | Examples |
|---|---|---|
| **Language** | How each construct of the base language and each member of the standard library ([library.md](library.md)) is written in a language: all the templates of `[syntax]`, `[types]`, `[operators]` and `[library]`. It has no `extends`. | `typescript`, `dart`, `python` |
| **Dragonfly dialect** | Implements a **platform** of Dragonfly (`web`, `mobile`, `backend`; ADR-0093) in a language and framework: extends a language dialect with the platform's kinds, shortcuts, automatic imports and its own templates. `[dialect] platform` names the platform; the folder is `dialects/<platform>/<dialect>/`. | `backend/fastapi`, `backend/nestjs`, `mobile/flutter` |
| **Project** | Extends a dialect with the shortcuts and kinds of a concrete project. Its kinds are extension kinds (ADR-0095): they exist in the dialect it extends only, so they tie the project to that dialect; they are not part of the platform contract. | `dialects/myapp/` with `extends = "flutter"` |

```
typescript ──► nodejs ──► backend/nestjs
python ─────► backend/fastapi
dart ───────► mobile/flutter ──► myapp
```

A platform is a contract, `dialects/<platform>/platform.toml`: the kinds (name and header syntax), the consumed
decorators, the plugins, the folders of a project and the editor docs that every dialect of the platform must
implement, identically. The loader refuses a dialect that misses one of them, and a dialect may not add a kind,
decorator or plugin the platform does not declare: the Nuclear of a project never changes with its dialect. Only
type definitions (§5.6) and the kinds of a project dialect (§7) are a dialect's own: code that uses them is tied
to that dialect (ADR-0095).

```toml
# dialects/backend/platform.toml
[platform]
default_dialect = "fastapi"     # what `dragonfly new -p backend` uses without `-d`
name = "backend"
kinds = ["entity", "repository", "model", "usecase", "appcomponent", "service", "aggregate", "controller",
  "listener", "tools", "agent", "state", "graph", "appConfig", "config", "tests"]
decorators = ["entity", "primary", "column", "created", "updated", "repository", "manyToOne", "oneToMany",
  "manyToMany", "oneToOne", "joinTable", "joinColumn", "transactional", "controller",
  "get", "post", "put", "patch", "delete", "status", "consumer", "start", "next", "state", "test",
  "required", "email", "url", "minLength", "maxLength", "min", "max", "pattern"]
plugins = ["sqlite", "postgres", "mysql", "mariadb", "redis", "kafka", "events", "ai", "openai", "ollama", "chroma"]

# the arguments and the rules of decorators, the same for every dialect of the platform (a dialect's own win)
[decorators.args]
oneToMany = ["inverse!"]

# N0308: rules a field with this decorator must meet (ADR-0100)
[decorators.fields]
manyToOne = { optional = true, list = false, target = "entity", sibling = "{name}Id", inverse = "inverse" }
manyToMany = { optional = true, list = true, target = "entity", inverse = "inverse", with = "joinTable" }

# where each kind's file goes: {component}, {screen} (folders) and {file} (the name in snake_case)
[layout]
usecase = "components/{component}/domain/usecases/{file}.nuc"
appcomponent = "components/{component}/{component}_appcomponent.nuc"
```

`[layout]` gives every kind of the platform its place (a kind it does not declare is an error): `nuclear help layout
--dialect <d>` prints it, and agents (the Nuclear Developer's planner) build a piece's path from it instead of
guessing a folder.

`[[generators.<what>]]` (ADR-0103) is what `dragonfly gen <what>` writes: `component` (a component's facade),
`resource` (models, repository, a use case per action, the facade's aliases, the platform's entry: a controller, or a
screen with its state manager and state model, the tests) and `usecase` (a use case that only calls a repository
method, the alias of a use case in the facade, its route). Each entry is one file at its kind's `[layout]` place:

```toml
[gen]
http = 'Http(baseUrl = "{{baseUrl}}")'                                   # the connection a REST resource adds
http_named = 'Http(connectionName = "{{name}}", baseUrl = "{{baseUrl}}")'  # when the app already has one

[[generators.resource]]
kind = "usecase"
each = "each_action"          # one file per item of the list
when = "rest"                 # a value that must be true (rest, db, screen, paged, actions.<action>)
name = "{{UseCase}}"          # the declaration; the file is it in snake_case
merge = false                 # true: a file that exists gets only the members it lacks, each one whole (a facade's
                              # alias; a controller's route with its decorator and its body), told by its head line
template = """..."""
```

The values: `Name`/`name`, `Names`/`names` (the plural), `component`/`Component`, `fields` (`name`, `type`,
`optional`, `id`, `last`, `sample`), `data` (the fields without the key), `models` (`Model`, `fields`, `main`), `rest`,
`db`, `path`, `baseUrl`, `connection`, `paged`, `Page`, `items` (the page's field with the list), `idType`, `label` (what
a list shows of an item), `listParam`/`listArg`, `sample`/`pageSample` (values for the tests), `actions.<action>`,
`each_action` (`action`, `UseCase`, `alias`, `is.<action>`), `screen`/`Screen`. The values of `usecase`: `UseCase`,
`alias`, `component`/`Component`, `params` (`id: int, input: Order`, as the project writes them), `args` (`id, input`),
`error` and `value` (the two types of its `Result`), `async` (its `exec` awaits: what calls it writes `~`); with
`--calls`, `Repository`, `method` and either `result` (the method answers a `Result`) or `plain` (its answer goes inside
an `Ok`); with `--route`, `route`, `verb`, `prefix`, `path`, `Controller` and `app` (the controller's name for the
facade). A platform without a piece for a case refuses it (`--route` where no piece has `when = "route"`). The Nuclear
a generator writes is the same for every dialect of the platform (rule 11); a test builds a generated resource and
its use cases with every dialect (`a_generated_resource_compiles_with_every_dialect`, dragonfly).

A field rule: `optional` (the field is `x?: T`), `list` (its type is a list, or not), `target` (its type, or its
items, is a declaration with that decorator), `sibling` (a field of the same declaration must exist; `{name}` is the
decorated field's name), `inverse` (the argument whose value names a field of the field's type), `with` (this field,
or the one `inverse` names, has that decorator). Names are compared as Nuclear writes them, also when the dialect
writes them in snake_case.

A dialect inherits everything from its parent. The child's templates, types, operators and options replace
the parent's. Shortcuts (`imports`, `auto_imports`, `functions`, `kinds`, `modifiers`, `clauses`) **cannot**
be redefined: to replace one of the parent's, the child lists it in `[dialect] replaces`.

## 2. Files and lookup

A dialect is a folder `dialects/<name>/` with one or more `.toml` files, or a single file
`dialects/<name>.toml`. All the files of a folder are merged; only one has the `[dialect]` section. The folder
can be split by topic:

```
dialects/mobile/flutter/
├── dialect.toml            # [dialect] (with defs, §5.6), [kinds.*], [imports]
├── docs.toml               # documentation for the editor (§5.7); not part of the dialect
└── templates/
    ├── stateless.tpl       # template of the stateless kind
    └── stateful.tpl
```

The transpiler looks for dialects, in order, in: the directories of `--dialect-path`, those of the
`NUCLEAR_DIALECT_PATH` variable (separated by `:`), `./dialects` and the dialects shipped with NuclearLang. In each
directory it looks at `<name>/` and `<platform>/<name>/`. `--dialect` accepts a name or a path to the folder or
file; a Dragonfly project names its dialect in `config.nuc` ([projects.md](projects.md) §1).

## 3. Sections

| Section | Content |
|---|---|
| `[dialect]` | `name` (equal to the folder or file name), `extends`, `description`, `file_extension`, `indent`, `replaces`, `defs` (type definitions packages, §5.6) |
| `[options]` | Behaviour of the target (see `nuclear spec`): implicit `this`, named arguments, quotes, `const` in default values... |
| `[syntax]` | One template per construct of the base language: classes, functions, statements, expressions, imports |
| `[types]` | Base types (`string = "String"`), type constructors (`list = "List<{{item}}>"`) and a runtime class written with another name (`Page = "PageOf"` in flutter: Flutter has its own `Page`; it is imported by that name). A declaration of the project keeps its own name over this mapping |
| `[operators]` | A symbol (`and = "&&"`) or a template (`in = "{{right}}.includes({{left}})"`) |
| `[keywords]` | Reserved words of the target: `word = { level, via, note, nuclear }` (see reserved-words.md). Those of level `reserved` or `strict` are renamed if a Nuclear name matches |
| `[imports]` | `use` shortcuts |
| `[auto_imports]` | Symbols imported automatically when used |
| `[reexports]` | Modules that fully include others (`material.dart` includes `widgets.dart`) |
| `[exports]` | Names a module exports besides the auto-imported ones (`Task` of fpdart): a declaration of the project with that name hides it from the import (`hide` clause of `import_default`); the type definitions give the rest |
| `[functions]` | Function shortcuts |
| `[toolchain]` | What the `dragonfly` CLI and the editors run in the generated project (`build/` or the dialect's output): shell commands `install`, `compile`, `run`, `test`, `serve` (the editor's own server), and `url` (where the app answers), `ready` (the line of `run` that means it is up), `installed` (the folder that means `install` ran), `install_local` (run by `install` once per dependency of `config.nuc` that is a folder, `{{path}}`: a package manager keeps the old copy of a folder whose version did not change); placeholders `{{packages}}` (the installation's runtimes), `{{url}}`, `{{port}}`, `{{host}}`; `migrate_make`, `migrate`, `migrate_down` for `dragonfly migrate` with `{{message}}` and `{{migrations}}` (the project's `migrations/` folder), quoted for the shell (ADR-0100 §5). `[toolchain.linux|macos|windows]` override a key on that system. `[[toolchain.launch]]` are the editor's debug configurations, `[toolchain.settings]` its settings and `extensions` the editor extensions it recommends, with `{{name}}`, `{{app}}`, `{{url}}`, `{{port}}` (ADR-0072, ADR-0101) |
| `[call_site]` | `Module.method(...)` calls that receive where they are written (§5.3.1) |
| `[names]` | `globals` (names of the environment), `not_constructors` (PascalCase names called without `new`) and `written` (names templates write, like `Right`/`Left`: imported if the generated code contains them) |
| `[kinds.<word>]` | Header words that generate whole declarations: `stateless`, `controller`... |
| `[decorators]` | Decorators the templates read (`consumed`), that provide objects (`provide`), that do not return (`void`) and the arguments of each one (`args`, N0217) ([projects.md](projects.md) §5) |
| `[project]` | Multi-file projects: output folder, kind by folder, files generated once per project, the file that marks a project without `nuclear.toml` (`marker`, `output`) and the manifest written in Nuclear (`[project.manifest]`, `config.nuc`) ([projects.md](projects.md)) |
| `[docs]` | Module prefix → URL of a name's API reference, for the editor's hover. Variables: `name`, `library` (the rest of the module without its extension) and `class` (the name is PascalCase). The longest prefix wins; added to the parent's |
| `[architecture]` | Rules between the declarations of a project: components and who uses whom ([projects.md](projects.md) §4) |
| `[modifiers]` | Header words that add a prefix: `static`, `abstract`... |
| `[clauses]` | Words after the name followed by a type: `with Flyer` |
| `[use]` | `clauses`: words allowed after a `use` path (`show`, `hide`, `deferred`) |

An unknown section or key is an error (`N0206`), with a suggestion of the right name.

## 4. Templates

Templates use a subset of Mustache:

| Form | Meaning |
|---|---|
| `{{name}}` | Inserts a variable. `{{clause.on}}` reads a field |
| `{{#name}}...{{/name}}` | If the variable is true (non-empty text, `true`, a list with elements), writes the inside. If it is a list, writes it once per element |
| `{{^name}}...{{/name}}` | Writes the inside if the variable is false or empty |
| `{{#a or b}}...{{/a or b}}` | The first of the alternatives that is true (also in `{{a or b}}`): a section that opens for either of two variables |
| `{{.}}` | The current element of a list of texts |
| `{{@first}}` `{{@last}}` `{{@index}}` | Position inside a list: `{{^@last}}, {{/@last}}` |
| `{{name\|filter}}` | Filters: `pascal`, `camel`, `snake`, `kebab`, `lower`, `upper`, `join:", "`, `unquote` (a string argument as a bare name: `{{decor.oneToMany.inverse\|unquote}}Id` → `projectId`); they chain (`\|unquote\|snake`) |

Formatting rules:

1. A line that contains only a section tag (`{{#x}}`, `{{^x}}`, `{{/x}}`) does not appear in the output.
2. A line that contains only `{{value}}` disappears if the value is empty.
3. A multi-line value keeps the indentation of the line where it is inserted. That is why bodies are written
   like this and come out correctly indented:

   ```toml
   while = """
   while ({{cond}}) {
     {{body}}
   }"""
   ```
4. In a run of braces, the tag starts at the last two: `{{{#members}}` is a literal `{` followed by the
   `members` section. So an empty class is written `{}`:

   ```toml
   class = """
   class {{name}} {{{#members}}
     {{members}}
   {{/members}}}"""
   ```

### 4.1 Templates in files

Any template can be written inline (`"..."`) or in its own file with `{ file = "path" }`. The path is
relative to the TOML file that references it, and the file's final newline is not part of the template.
Long templates (the kinds) go in `.tpl` files:

```toml
[kinds.stateless]
template = { file = "templates/stateless.tpl" }

[syntax]
while = { file = "templates/while.tpl" }
```

An error inside the file is reported on the exact line of the `.tpl`.

### 4.2 Variables

Each template receives fixed variables (for example `function` receives `name`, `params`, `ret`, `async`,
`body`...). The full list is in `nuclear spec`. `method` and `method_signature` also receive `mods`, with one
variable per header word, so the template can place a modifier somewhere else: in Dart, `get` goes between the
type and the name.

```toml
[modifiers]
get = ""          # not written in {{modifiers}}

[syntax]
method = "{{ret}} {{#mods.get}}get {{name}}{{/mods.get}}{{^mods.get}}{{name}}({{params}}){{/mods.get}} { ... }"
```

Using a variable that does not exist gives a warning `N0210`. A target dialect must define every required
template; `nuclear dialect check` lists the missing ones (`N0203`).

The templates of `Result<E, T>` (nuclear-base.md §3.2) are optional: `result_runtime` (the `Result` type with
`Ok` and `Err`, written once after the imports of the file that uses it), `result_ok`, `result_err`,
`result_is_ok`, `result_is_err`, `result_value`, `result_error`, `result_propagate` (returns the error of
`{{result}}` if it is `Err`) and `result_then`, `result_tap`, `result_recover`, `result_tap_error` (`.ok()` /
`.error()` that transform or observe). A dialect without them cannot transpile code that uses `Result`
(`N0203`). `result_runtime` is optional: a target that uses a library does not define it (Dart: fpdart's
`Either`, with `[types] Result = "Either"` and `[names] written`). Example of an own runtime:
`dialects/typescript/templates/result.tpl`.

## 5. Shortcuts: code compression

A shortcut replaces a repeated text with a shorter one, as in a compression algorithm. The developer writes
the short form and the dialect expands it.

### 5.1 `[imports]`: `use` shortcuts

```toml
[imports]
material = "package:flutter/material.dart"                        # module
materialui = "import 'package:material_ui/material_ui.dart';"     # whole line, copied as it is
"fs/promises" = "node:fs/promises"
```

```nuclear
use material                    // import 'package:flutter/material.dart';
use fs/promises{ readFile }     // import { readFile } from 'node:fs/promises';
```

A path that is not a shortcut goes through the `[syntax] module_path` template (Dart: `package:{{path}}.dart`).

### 5.2 `[auto_imports]`: automatic imports

```toml
[auto_imports]
"node:fs/promises" = ["readFile", "writeFile", "mkdir"]
"package:flutter/material.dart" = ["MaterialApp", "Scaffold", "Text"]
```

If the code uses `readFile` and the file neither declares nor imports it, the transpiler adds the import. The
names of the same module are grouped in a single line (`import { readFile, writeFile } from ...`) when the
target defines `import_names`; otherwise the whole module is imported (Dart). A symbol can come from only one
module.

`[reexports]` says which modules fully include others. A module is not imported if another module the file
already imports includes it:

```toml
[reexports]
"package:flutter/material.dart" = ["package:flutter/widgets.dart"]
```

With `Scaffold` (material) and `Text` (widgets) only `material.dart` is imported; with `Text` alone,
`widgets.dart`.

A project may declare a name a library also exports (`Task` next to fpdart's `Task`): the import of that library
gets a `hide` clause with the project's names when the dialect's `import_default` writes `clauses.hide`. The names
come from the type definitions, and from `[exports]` for a library without them:

```toml
[exports]
"package:fpdart/fpdart.dart" = ["Task", "Option", "State", "Unit"]
```

**Imports generated from type definitions.** In `dart` and `flutter` there are no hand-written lists: each
type definitions package (§5.6) brings the public names of its libraries and the library that provides each
one, generated with the official Dart analyzer. A name written in `[auto_imports]` has priority over the
packages. `tools/analyze-flutter.sh` transpiles the Flutter examples and checks them with `flutter analyze`.

### 5.3 `[functions]`: function shortcuts

```toml
[functions]
print = "console.log"                         # renames the function
now = { template = "new Date()" }             # replaces the whole call
sleep = { template = "await new Promise((r) => setTimeout(r, {{arg0}}))" }
```

The template receives `args` (all the arguments) and `arg0`, `arg1`...

#### 5.3.1 `[call_site]`: where a call was written

```toml
[call_site.Log]
arg = "at"
text = "{{component}} › {{kind}} › {{module}}.{{method}} · {{path}}.nuc:{{line}}"
```

Each `Log.<method>(...)` call also receives the named argument `arg`, a constant text with `text` rendered
where the call is. Variables: `path` (the file in the project, without extension; empty outside a project),
`line` (its line in the `.nuc`), `component` (the folder under `[architecture] scope`), `kind`, `module` (the
declaration) and `method` (the function or method; a lambda takes its method's). It is not added if the call
already writes it or if `Log` is a name of the file. It is a literal: it costs nothing at run time.

```nuclear
usecase GetPageUseCase
  exec(page: int)
    Log.d("page loaded")
```

```dart
Log.d('page loaded', at: 'characters › usecase › GetPageUseCase.exec · components/characters/domain/usecases/get_page_usecase.nuc:3');
```

### 5.4 `[kinds.<word>]`: generated declarations

A kind is a word before the name of a declaration ("header + block" rule). The parser does not know it: the
dialect validates and emits it. The template generates the whole declaration in the target, so the developer
writes only the logic:

```nuclear
stateless MyApp
  build(context: BuildContext) Widget
    MaterialApp(title = "Demo")
```

```toml
[kinds.stateless]
description = "StatelessWidget"
imports = ["StatelessWidget"]       # symbols imported when the kind is used
overrides = ["build"]               # methods that carry the target's override mark
requires = ["build"]                # required methods (N0209 if missing)
named_params = true                 # constructor parameters are passed by name
template = { file = "templates/stateless.tpl" }
```

```
// templates/stateless.tpl
class {{name}} extends StatelessWidget {
  const {{name}}({super.key});

  {{members}}
}
```

| Key | Use |
|---|---|
| `template` | Required, inline or `{ file = "templates/x.tpl" }`. Variables: `name`, `source_name`, `class_name`, `members` (fields and methods), `body` (constructor, fields and methods), `methods_code`, `fields` (list: `name`, `type`, `type_nullable`, `default`, `optional`, `tinfo`, `decor`, `decorators`: the decorators the dialect does not consume, already written), `fields_required` (true when a field has neither `?` nor a default), `methods` (list: `name`, `is.<name>`, `params_list`, `ret_info`, `decor`), `params`, `params_list` (list: `name`, `type`, `tinfo`, `decor`, `default`, `optional`, `named`, `required`), `ctor`, `extends`, `implements`, `clauses`, `clause.<word>`, `decorators`, `decor`, `deco_args`, `export`, `modifiers`, `generics` (text: `<T>`), `generic_list` (list: `name`), `file`, `project`, `component`, `kind` ([projects.md](projects.md) §5). A template that does not use `generics`/`generic_list` (or `implements`/`clauses`) rejects declarations with generics (or with `> Interface`): `N0218` |
| `rename` | Output name: `"{{name}}Controller"` |
| `imports` | Symbols of `[auto_imports]` the kind may need: imported if the generated code writes them |
| `inherits` | Classes of the type definitions (§5.6) the generated class extends (`["State"]`): their members are used as members and a method with one of those names gets `override = true` |
| `overrides` | Methods that get `override = true` in the `method` template, besides those of `inherits` |
| `requires` | Methods the block must have |
| `members` | Inherited names that are not in `inherits`: used as members, without an explicit `this.` |
| `param_access` | How constructor parameters are read inside members: `"widget.{{name}}"` |
| `named_params` | Calls to the constructor pass the arguments by name; in a dialect whose named arguments are one object (`named_args = "object"`) they stay that object instead of being reordered by position |
| `syntax` | `[syntax]` templates that change only inside this kind: `[kinds.controller.syntax] ctor_param = "private readonly {{name}}: {{type}}"`; `construct` is how a call to a declaration of this kind is written (`"{{callee}}({{args}})"` when the kind is a function, not a class) |
| `type_imports` | The declarations of this kind refer to each other only in types (two related entities): their imports of each other go in the dialect's `[syntax] type_imports` block (Python: `if TYPE_CHECKING:`), never a circular import |
| `async_methods`, `methods`, `returns`, `file_header`, `alias_via`, `declares`, `method_members`, `provide`, `results`, `void_methods` | For frameworks: asynchronous methods, allowed methods (N0215), required return type (N0216), text once per file, where an alias's instance comes from, extra classes the template writes, members the method template writes beside each method (`purge{{name\|pascal}}`, so N0116 knows them), how program declarations are read, `Result` without propagation and methods without a return ([projects.md](projects.md) §5) |

A kind also serves to **generate repetitive code**. `data` (dart dialect) walks the fields and generates the
constructor, `copyWith` and `toJson`:

```toml
[kinds.data]
template = { file = "templates/data.tpl" }
```

```
// templates/data.tpl (shortened)
class {{name}} {
  const {{class_name}}({{{#fields}}required this.{{name}}{{^@last}}, {{/@last}}{{/fields}}});
{{#fields}}
  final {{type}} {{name}};
{{/fields}}
  Map<String, dynamic> toJson() => {{{#fields}}'{{name}}': {{name}}{{^@last}}, {{/@last}}{{/fields}}};
}
```

### 5.5 `[modifiers]` and `[clauses]`

```toml
[modifiers]
static = "static "                       # prefix added to the declaration
abstract = { prefix = "abstract ", applies_to = ["module"] }
set = { prefix = "set ", void = true }   # void: the declaration never returns (no implicit return)

[clauses]
with = " with {{types}}"                 # Bird: Animal with Flyer → class Bird extends Animal with Flyer
```

### 5.6 Type definitions (`defs`)

Like TypeScript's `.d.ts` files and `@types/*` packages: the public API of the target's libraries, one package
per library and version, in a repository shared by every dialect of the same language
(`defs/<language>/<package>/<version>/`). The format, the priority order and the tools are in
[definitions.md](definitions.md).

```toml
[dialect]
name = "flutter"
extends = "dart"
defs = ["flutter@3.47.7", "flutter_bloc@9.1.1", "get_it@9.3.0", "dio@5.11.1", "json_annotation@4.12.0"]
```

A dialect adds its packages to its parent's and the dependencies of each package are loaded automatically.
With them the transpiler:

- imports each public name of their libraries by itself (§5.2);
- marks as an override (`override` / `override_interface`) a method named like a member of an external class
  the module extends or implements, and lets inherited members be used without declaring them;
- gives error `N0106` for a name that is not in the file nor in the class chain;
- sends a base with `kind = "interface"` to `implements` (in Dart, an `interface class` like `Comparable`).

`[options] implicit_base` names the class every class extends in the target (Dart: `Object`), so `toString()`
is also marked as an override.

### 5.7 Editor documentation (`docs.toml`)

`docs.toml`, next to `dialect.toml`, is what the editor shows when hovering a word of the dialect and when
completing it. It is not a rule of the dialect: the loader does not read it as a dialect file and a `build`
never opens it; the editor reads it the first time it needs it. Each entry is markdown in English with what
the word does, an example in Nuclear, what it generates, its rules (with the error codes) and, when it helps,
a text diagram.

````toml
[kinds]
usecase = '''
**One business operation**: a single method `exec` that returns a `Result`.

```nuclear
usecase GetPageUseCase
  (repository: CharacterRepository)

  exec(page: int) Result<CharacterError, Character[]>
    Ok(~repository.getPage(page))
```
'''

[decorators]   # without @: screen, get, state...
[words]        # modifiers and clauses: static, get, with...
````

- **An entry is Nuclear only**: what the word means in the platform, never the framework underneath (no
  "a SQLAlchemy table", "a Cubit", "pytest"), because the local agents read these texts and write only Nuclear.
  What the dialect writes under a word goes to `[underneath.<section>]` of the same file (`entity = "a SQLAlchemy 2
  mapped class"`): `nuclear help` and the editor show it after the entry as **Underneath (dialect):**, the
  Smart Graph's agent collection leaves it out.
- A dialect inherits its parent's entries and can replace them.
- Every kind, decorator (`[decorators]`, `[decorators.args]`, `[decorators.provide]`), modifier and clause of
  the dialect has its entry; the test `every_dialect_word_has_editor_docs` checks it for the shipped dialects.
- The editor adds what comes from the dialect itself: the kind's required methods, the names it brings and the
  arguments of each decorator.
- The words of the base language (reserved words, `Result`/`Ok`/`Err`, base types and comment tags) are in
  `languages/docs.toml`, with the same format, built into the transpiler.

The documentation of the user's declarations is their doc comments (base §2.3). The optional `doc_comment`
template writes them in the target (JSDoc in TypeScript, `///` in Dart); without it they are written with
`comment`, as one more comment.

### 5.8 `[library.<base>]`: the standard library

Nuclear's standard library ([library.md](library.md), ADR-0094) is a fixed vocabulary: Rust holds the members of
each base type (`crates/nuclear-dialect/src/library.rs`: name, property or method, what it gives); a language
dialect writes how each one comes out, one template per member, in `library.toml`:

```toml
[library.string]
upper = "{{recv}}.toUpperCase()"
toInt = { template = "_toInt({{recv}})", helper = "function _toInt(s: string): number | null { ... }" }

[library.list]
map = "{{recv}}.map({{arg0}})"                                    # TypeScript
map = "{{#fn}}[{{fn.body}} for {{fn.param}} in {{recv}}]{{/fn}}{{^fn}}list(map({{arg0}}, {{recv}})){{/fn}}"   # Python

[library.Math]
sqrt = "Math.sqrt({{arg0}})"
```

| Key | Use |
|---|---|
| bases | `string`, `list`, `map`, `set`, `int`, `double`, `number` (what `int` and `double` share), `boolean`, `bytes`, `datetime`, `duration`, `regex`, `match`, `error`, `any` (`toString`); objects `Math`, `Json`, `String`, `DateTime`, `Duration`, `Regex`, `Set`, `Bytes`, `Error` (`new` is the constructor) |
| variables | `recv` (the value before the dot), `args`, `arg0`..., `has_args`, `n`, `named.<name>` (a named argument; a literal `true`/`false` is a flag), `call_args` (every argument as the target writes a call), `argN_is.<base>` (the static type of an argument: `split` takes a string or a Regex), `elem` (the element type), `type_args`, and for the first expression lambda among the arguments `fn.param`, `fn.params`, `fn.p0`, `fn.p1`, `fn.body` |
| `helper` | A function the template calls, written once per file after the imports. `[functions]`, `[syntax]` and `[operators]` entries take `helper` too (`print` in Python, `non_null`, `coalesce_once`) |
| extensions | A member Nuclear does not define (`[library.string] tr` in the mobile platform) is the dialect's own: rendered the same way, its result type unknown |

The emitter rewrites a member when the receiver's type is known (`nuclear-base.md`'s types, a literal, a library
result, a declared or alias signature, `inject<T>()`, a `Result`'s `value`/`error`, the parameters of a callback
from the receiver's element type). A target's name on a base type is N0114 (`library::WRONG`); a method of a value
without a type whose templates differ between bases is N0115; a property of a value without a type is the value's
own and is written as it is. The platform contract does not list library members: every language dialect renders
the whole vocabulary (`nuclear spec` prints it).

## 6. Validation

`nuclear dialect check <name>` validates a dialect and every dialect it extends. The transpiler applies the
same rules every time it loads a dialect:

| Rule | Code |
|---|---|
| Valid TOML, known sections and keys, values of the right type, well-formed templates | N0206 |
| A shortcut is defined only once across the dialect's files | N0204 |
| A child dialect does not redefine a parent's shortcut, unless it lists it in `[dialect] replaces` | N0204 |
| Kinds, modifiers and clauses share a namespace | N0204 |
| `[functions]` and `[auto_imports]` share a namespace | N0204 |
| A symbol of `[auto_imports]` comes from a single module | N0204 |
| No shortcut is named like a reserved word of the base language | N0212 |
| Two shortcuts that differ only in case or in one character (names of 6+ letters) | N0205 (warning) |
| A template uses a variable that does not exist | N0210 (warning) |
| A target dialect defines every required template | N0203 |
| The dialect exists and inheritance has no cycles | N0207 |

Example: `nestjs` inherits from `nodejs`, which imports `Transform` from `node:stream`. In Nest, `Transform` is
the decorator of `class-transformer`; so `nestjs` declares `replaces = ["auto_imports.Transform"]`.

## 7. Extension kinds: kind packages

Kinds are Nuclear's libraries (ADR-0095): the **native** kinds of a platform live in its contract (§1), and
**extension** kinds come in packages, written by a project or by the community on top of the dialects of one
platform, with TOML and templates only. A package is a folder:

```
kinds/jobs/
├── kind.toml                 [package] name, version, platform, description
├── docs.toml                 editor documentation of its words (§5.7)
├── fastapi/kind.toml         how the fastapi dialect writes its kinds: [plugin] (runtime packages, defs, names)
│   └── templates/job.tpl     and the same sections as a dialect: [kinds.*], [decorators], [functions],
└── nestjs/kind.toml          [auto_imports], [library.*]... never [dialect], [project] or [syntax]
```

```toml
# kinds/jobs/kind.toml
[package]
name = "jobs"
version = "0.1.0"
platform = "backend"
description = "Scheduled jobs of the app."

# kinds/jobs/fastapi/kind.toml
[plugin]
packages = { apscheduler = ">=3" }

[kinds.job]
description = "job Name(deps) + run() → a scheduled task"
requires = ["run"]
async_methods = true
template = { file = "templates/job.tpl" }
```

- `nuclear kind new <name> -p <platform> -d <dialect>` writes the skeleton in `kinds/<name>/` of the project.
- The loader reads the packages of `<project>/kinds/` and of the install folder (`dragonfly add <folder>` installs
  one for every project). A package of the project's platform is a **plugin** of the dialect: `config.nuc` enables
  it with `plugins(jobs = true)`, its kinds and names need it (N0304), its runtime packages reach the generated
  manifest, and the project keeps `dragonfly(platform = "backend", dialect = "fastapi")`.
- The implementation is the folder named after the dialect, or after a dialect it extends. A package without one
  for the project's dialect is N0306 when enabled: enabling a package implemented for some dialects ties the project
  to them, exactly as a dialect's type definitions do. The Nuclear of the kind is the same in every dialect that
  implements it.
- The platform contract does not list extension kinds; the loader records where each kind comes from
  (`Dialect.kind_sources`: the language's, native of the platform, or a package with its version and dialects) so
  the editor can show it.

A **project dialect** (`dialects/myapp/` with `extends = "flutter"`) is still read for a project's own shortcuts
(`imports`, `auto_imports`, `functions`); its kinds are extension kinds of that project with the same rule (tied to
the dialect it extends, source "package" without a version), and a Dragonfly project names it in `config.nuc`
(`dragonfly(platform = "mobile", dialect = "myapp")`). A kind package is the portable form.

## 8. Creating a new dialect with an agent

A new dialect (a language like `crystal` or a framework like `amber`) is created by a **coding agent**
(Claude, Codex, OpenCode...) following this section. Whoever asks for it describes the *what for* and reviews
the result; the agent writes the files and checks them with the transpiler. The user tutorial is
[docs/dialects/create-with-agent.md](../docs/dialects/create-with-agent.md).

### 8.1 Purpose and philosophy

- Nuclear is a cross-cutting transpiler: the parser, the AST, the analysis and the emitter are the same for
  every target. A dialect **only teaches how** each construct is written in its target.
- Golden rule (above): the generated code is an expert's in the target, transpiling is immediate and what is
  written in Nuclear is the minimum.
- Rust decides *what* is emitted; the dialect decides *how* it is written.

### 8.2 What a dialect can do

Only what sections 1–6 describe, with files in `dialects/<name>/`:

| File | Content |
|---|---|
| `dialect.toml` | `[dialect]` (`name`, `extends`, `replaces`, `defs`), `[syntax]`, `[types]`, `[operators]`, `[options]`, `[imports]`, `[auto_imports]`, `[functions]`, `[call_site]`, `[kinds.*]`, `[modifiers]`, `[clauses]`, `[decorators]`, `[names]`, `[project]`, `[architecture]` |
| `templates/*.tpl` | long templates, with the Mustache subset of §4 |
| `keywords.toml` | reserved words of the target (escaped automatically) |
| `spec.md` | the rules the dialect adds to the base, its translation table and the equivalences of the base examples |

A target dialect defines every required template (`nuclear spec` lists them). A framework dialect extends a
target (or another framework) and adds kinds, decorators and shortcuts.

### 8.3 Process

1. **Read the contract:** `nuclear spec` (base language, this document and the list of templates, variables
   and options). For a framework, `nuclear spec --dialect <parent>`.
2. **Take a reference:** a target dialect starts from the structure of `dialects/typescript/` or
   `dialects/dart/`; a framework one, from `dialects/backend/nestjs/` or `dialects/mobile/flutter/`.
3. **Write `spec.md` first**, with each rule and its example: a ` ```nuclear ` block followed by the block of
   the target that must come out. Each rule has at least one example.
4. **Write `dialect.toml` and the templates** until `nuclear dialect check <path> --json` has no errors, and
   `docs.toml` with the editor documentation of each word (§5.7).
5. **Compile each example** with `nuclear build <file.nuc> --dialect <path>` and compare with `spec.md`. If
   it differs, fix the template, not the example (unless the example is badly written in the target).
6. **Validate in the target:** the output compiles and passes the target's analyzer or linter without
   warnings.
7. **Deliver** the list of base constructs covered, the ones that could not be expressed and why.

### 8.4 Restrictions

An agent creating a dialect **cannot**:

1. **Touch the transpiler** (`crates/`, the parser, the AST, the emitter) nor Nuclear's grammar. If a
   construct cannot be written with templates and options, it stops and reports it; it does not fake it.
2. **Change Nuclear's syntax**: no new words outside kinds, modifiers, clauses and decorators, nor another
   meaning for a base construct.
3. **Edit the shipped dialects** (`typescript`, `dart`, `nodejs`, `nestjs`, `flutter`). They are extended.
4. **Redefine a parent's shortcut** without `[dialect] replaces` (N0204), nor name a shortcut like a reserved
   word of the base (N0212).
5. **Offer a second way of writing the same thing.** A kind, decorator or shortcut exists only if it removes
   repeated code of the target.
6. **Generate code an expert in the target would not write**: no reflection, no unused layers or indirections,
   no warnings from the target's analyzer.
7. **Leave a rule without an example**, nor an example whose output is not the transpiler's real one.
8. **Write in `spec.md` anything that is not a final rule**: no questions, assumptions, pending items nor
   history. Doubts are asked to whoever requested the dialect.
9. **Leave Dragonfly's rules** in a Dragonfly dialect: components, layers, architecture kinds and
   `[architecture]` rules are those of [flutter.md](https://github.com/nuclearlang/dragonfly-mobile/blob/main/spec/flutter.md) §1, §3, §4 and §6, applied to its technology.
10. **Write in a language other than English**: the dialect's files (comments and `note` of the `.toml`,
    templates, the `.nuc` test examples) and its documentation (`.md`).

### 8.5 Done

- `nuclear dialect check <path> --json` without errors.
- Each example of `spec.md` gives exactly its output.
- The output passes the target's compiler and analyzer without warnings.
- `nuclear spec --dialect <name>` prints the base followed by the specs of the chain.
- Each kind, decorator, modifier and clause has its entry in `docs.toml` (§5.7).

## 9. Tools

The transpiler loads dialects at run time and exposes a single diagnostics function
(`nuclear_transpile::check`), the same one `nuclear check --dialect <name> --json` and the Language Server use.
So the editor marks, while the developer or the agent writes, the errors of the base language and those of the
active dialect: unknown kinds with a suggestion (`N0201`), kinds without their required methods (`N0209`),
invalid `use` clauses (`N0211`) and missing templates (`N0203`).

Editors have a base extension for every dialect (Language Server, highlighting, theme, metrics, line map) and
one extension per framework to run and debug with its tools (Dragonfly for Flutter). The base knows no
language: a file's dialect comes from its project (`nuclear.toml` or the dialect's `[project] marker`) and the
links to the API reference from `[docs]`:

```toml
[docs]
"dart:" = "https://api.flutter.dev/flutter/dart-{{library}}/{{name}}{{#class}}-class{{/class}}.html"
```

`dart:convert` + `jsonDecode` → `https://api.flutter.dev/flutter/dart-convert/jsonDecode.html`. A new dialect
works in the editor without changing the base extension.
